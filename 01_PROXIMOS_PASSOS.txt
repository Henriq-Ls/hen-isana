## PARTE 3 — CONHECIMENTO, CADASTRO MULTIFONTE, JSON E OPERAÇÃO
===============================================================================

Objetivo: construir a camada que recebe, valida, revisa e persiste conhecimento
estruturado, com participação de fontes diferentes e sem cascata implícita.

### DECISÃO ARQUITETURAL — CADASTRO ASSISTIDO

O cadastro novo não usará uma sequência universal de perguntas fixas. Cadastro
manual, JSON e assistência de IA/professor devem convergir para um contrato
estruturado comum:

```text
entrada manual
      \
JSON -----> contrato de cadastro -> validação -> API de conhecimento -> linguagem.db
      /
IA/professor
```

O professor não escreve diretamente no SQLite e não decide tabela ou coluna
física. O mapeamento para `linguagem.db` permanece sob controle do código
Python e da API de conhecimento.

Os módulos existentes `professor/professor.py` e
`professor/professor_llama.py` devem ser preservados como infraestrutura. A
arquitetura futura terá dois papéis conceituais:

- **Professor respondente:** recebe uma pergunta específica e responde.
- **Professor estruturador:** recebe uma entrada e propõe a estrutura de
  conhecimento necessária, preservando incerteza e informação ausente.

O cadastro manual poderá funcionar como entrevista dinâmica: identificar o
objeto, consultar o que já existe, detectar o que falta, gerar a próxima
pergunta necessária, validar a resposta e somente então propor o cadastro.
Informações já presentes não devem ser perguntadas novamente por uma lista fixa.

O JSON será formato de entrada/proposta, não cópia direta do schema SQLite:

```text
texto/entrada -> professor -> proposta JSON -> contrato -> validação
-> revisão/autorização -> API de conhecimento -> linguagem.db
```

O sistema deve funcionar sem IA. IA, internet e professor são fontes de
proposta, nunca aprovadores automáticos. Proveniência, evidência, incerteza,
autorização explícita e separação entre informação fornecida, proposta e
confirmada são obrigatórias.

### FASE 3.1 — API estruturada do conhecimento

Consultar e registrar formas, lemas, sentidos, conceitos, expressões,
proposições, fatos, relações, fontes e evidências por contratos explícitos.
O contrato comum deve servir às entradas manual, JSON e IA/professor, sem expor
o schema físico aos adaptadores.

### FASE 3.2 — Novo processo de cadastro por pacote

- **Manual:** funciona como entrevista dinâmica orientada pelo estado do
  cadastro, com pendências agrupadas e autorização antes da persistência.
- **Professor:** recebe uma solicitação estruturada e devolve candidato,
  evidências e incertezas.
- **Professor Llama:** usa o mesmo contrato do professor, mas com adaptador
  local separado.
- **Outras IAs:** entram como fontes/adaptadores, nunca como escritoras diretas.
- **Internet:** fica fora do fluxo principal de cadastro.
- **Validação:** normaliza, identifica duplicidade, resolve referências lógicas,
  preserva proveniência e encaminha para revisão.
- **Aprovação:** fonte automática não aprova a própria proposta.
- **Cascata:** não é chamada automaticamente.
- **Tutoria:** o HEN-ISANA coordena tarefa, resposta, validação, lacunas e
  próxima pergunta; isso não é uma sequência cega de chamadas ao professor.

### FASE 3.3 — Ingestão controlada de JSON

Implementar, depois da API e do schema, um módulo controlado com leitor,
validação estrutural e semântica, duplicidade, referências, dry-run, relatório,
aplicação transacional, auditoria e rollback. Nomes definitivos, diretório de
entrada, estados JSON e formato do relatório foram definidos e documentados na
implementação da Fase 3.3.
Campos fora do contrato, tipos inválidos e estruturas incompatíveis devem ser
rejeitados. JSON nunca pode ser executado como código.

### FASE 3.4 — Inferência simbólica

Aplicar somente regras explícitas, com premissas, conclusões, conflitos e
proveniência. Não transformar candidato, hipótese ou ausência de prova em fato.

### FASE 3.5 — Modo sombra e integração gradual

Status: concluída e validada em 2026-09-25.

`aplicacao/modo_sombra.py` executa o analisador simbólico novo de forma
observacional, adapta a tokenização legada para uma representação lexical comum,
registra resultados e diferenças em memória e devolve sempre a saída legada.
Falha, ausência de suporte, incompletude e ambiguidade produzem fallback
explícito. A entrada é opt-in; o fluxo normal não foi substituído.

O escopo de comparação desta fase termina na fronteira lexical/simbólica. A
saída do fluxo legado continua preservada quando a estrutura nova falha, está
incompleta, é insuficiente ou não é suportada.

### FASE 3.6 — Geração de resposta baseada em estrutura

Status: concluída e validada em 2026-09-26.

Receber um `PlanoResposta` com intenção, proposições, resultados, evidências,
incertezas, conflitos, inferências e proveniência, produzindo texto somente a
partir da estrutura recebida, sem reinterpretar a frase original.

Implementação opt-in em `core/resposta_estruturada.py`,
`aplicacao/resposta_estruturada.py` e
`aplicacao/modo_sombra.py`. Conclusões inferidas são identificadas como
inferências, conflitos permanecem sem resolução automática, informação ausente
é declarada sem invenção e o fallback legado registra explicitamente o motivo.

Evidência reproduzível:

  17 testes aprovados;
- conjunto direcionado das Fases 3.1–3.6 — 98 testes aprovados;
- suíte completa — 278 testes, 275 aprovados e somente as três falhas legadas

Nenhum schema foi alterado, nenhuma inferência foi persistida como fato e o
