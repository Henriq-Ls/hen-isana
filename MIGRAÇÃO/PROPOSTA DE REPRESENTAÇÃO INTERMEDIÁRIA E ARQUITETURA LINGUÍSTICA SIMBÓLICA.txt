1. DECISÕES CENTRAIS
--------------------

1.1. O código atual é legado

O sistema atual será usado como referência, baseline de comportamento, fonte de
dados e coleção de testes. Ele não deve definir sozinho a arquitetura nova.

Não vamos simplesmente transformar a tabela atual de conhecimento em outra
tabela com mais colunas. O modelo novo precisa distinguir explicitamente:

* forma lexical;
* lema;
* lexema;
* flexão;
* classe gramatical;
* sentido;
* conceito;
* expressão;
* entidade;
* evento;
* estado;
* propriedade;
* predicado;
* argumento;
* relação semântica;
* proposição;
* polaridade;
* modalidade;
* escopo;
* contexto;
* evidência;
* fato;
* inferência;
* intenção;
* planejamento;
* geração de resposta.

1.2. O primeiro núcleo será simbólico

A arquitetura inicial será baseada em regras explícitas, estruturas
intermediárias e conhecimento persistente em SQLite.

O núcleo inicial não dependerá de:

* redes neurais;
* embeddings;
* LLM;
* modelos estatísticos;
* busca aproximada como substituta da análise linguística.

Essas tecnologias podem ser avaliadas no futuro como apoio, mas não devem
definir a representação intermediária.

1.3. A frase não será tratada como uma ficha

O objetivo é sair de:

    "encontrei uma ficha correspondente"

para:

    "analisei a frase, identifiquei suas unidades, construí uma estrutura
     sintática e semântica, representei as proposições e só depois decidi
     como responder."

Uma frase nova deve poder ser analisada mesmo quando a frase inteira não está
cadastrada no banco.

1.4. O banco novo será separado

A recomendação é criar futuramente somente um novo banco para o núcleo
linguístico:

    aprendizado/bancos/linguagem.db

Esse banco concentrará o conhecimento linguístico, semântico e factual
estruturado.

Não será criado um banco separado para cada camada. Léxico, sentidos,
conceitos, proposições, fatos, relações e evidências precisam de relações
fortes e devem permanecer no mesmo banco canônico.

1.5. O legado será preservado

Os bancos atuais não serão apagados durante a implementação ou migração.

Os dados conhecidos atualmente serão preservados:

    conhecimento.db: 37 conhecimentos
    evidencias_conhecimento: 217 evidências
    relacoes.db: 66 relações
    fatos_conhecimento: 0 fatos

Os dados antigos só deixarão de ser usados como fonte principal depois de:

* o novo núcleo existir;
* os testes passarem;
* a migração ser revisada;
* a comparação antigo/novo ser concluída;
* o rollback continuar disponível.


2. ESTADO ATUAL DO PROJETO
--------------------------

2.1. Bancos existentes

Foram encontrados os seguintes arquivos:

    hen-isana/aprendizado/bancos/conhecimento.db
    hen-isana/aprendizado/bancos/indice_codigo.db
    hen-isana/aprendizado/bancos/log_mudancas.db
    hen-isana/aprendizado/bancos/relacoes.db
    hen-isana/data/diagnostico.db

O arquivo `propostas_aprendizagem.py` não possui um banco separado. A tabela
`propostas_aprendizagem` é criada na conexão do `conhecimento.db`.

2.2. Papel dos bancos atuais

`conhecimento.db`

Banco legado que mistura:

* termos;
* expressões;
* categorias;
* significados;
* contexto de uso;
* respostas padrão;
* exemplos;
* fatos;
* evidências;
* propostas de aprendizagem.

Não é adequado como modelo canônico da arquitetura nova.

`relacoes.db`

Banco legado com relações entre IDs de termos. Não informa de forma suficiente
o tipo semântico, direção, participantes, evidência, estado ou validade da
relação.

`indice_codigo.db`

Índice operacional dos arquivos, classes e funções de código gerado. Não é
conhecimento linguístico.

`log_mudancas.db`

Histórico operacional de alterações de código. Não é conhecimento linguístico.

`diagnostico.db`

Registro operacional de erros e bloqueios. Não é conhecimento linguístico e
deve permanecer separado.

2.3. Pipeline atual em uma linha

    entrada no terminal
      -> normalização superficial
      -> resolução contextual limitada
      -> comandos e intenções heurísticas
      -> tokenização por palavras/expressões conhecidas
      -> busca textual no SQLite
      -> seleção heurística de fichas, fatos e relações
      -> composição de resposta
      -> contexto em memória

O pipeline atual não produz uma representação sintática ou semântica geral.


3. MAPA DETALHADO DO PIPELINE ATUAL
-----------------------------------

3.1. Entrada

O fluxo começa normalmente em:

    hen-isana/main.py
      -> aplicacao.terminal.executar_terminal()
        -> aplicacao.conversa.sessao.executar_conversa_pessoal()
          -> aplicacao.fluxo.processar_frase()

O modo conversa cria uma instância de:

    core.contexto_conversa.ContextoConversa

Essa instância permanece viva durante os turnos da sessão.

3.2. Orquestrador atual

O principal orquestrador é:

    aplicacao.fluxo.processar_frase()

Ele concentra responsabilidades que deverão ser separadas no futuro:

* comandos;
* normalização;
* contexto;
* intenções;
* tokenização;
* busca;
* aprendizagem;
* fatos;
* relações;
* seleção de sentido;
* composição de resposta.

3.3. Ordem efetiva atual

Em termos simplificados, `processar_frase()` faz:

1. verifica comandos de propostas;
2. normaliza a frase;
3. tenta resolver pronomes com o contexto;
4. trata comandos explícitos de aprendizagem;
5. trata intenções sociais;
6. trata ferramentas como hora, data, clima, URL e definição;
7. trata apresentação de nome e respostas pendentes;
8. tenta resolver desambiguação pendente;
9. busca uma resposta contextual;
10. se estiver em aprendizagem, tenta aprender;
11. registra o turno.

3.4. Normalização atual

`core.normalizador.normalizar_frase()`:

* aplica `casefold`;
* remove espaços externos;
* comprime espaços;
* expande abreviações registradas;
* preserva pontuação.

Também existem normalizações para:

* chave de busca;
* forma estrita;
* comparação de intenção.

Essa etapa não identifica sujeito, verbo, tempo, negação ou semântica.

3.5. Tokenização atual

A função atual:

    aplicacao.fluxo.tokenizar()

usa palavras extraídas por expressão regular e depois tenta preservar
expressões compostas conhecidas, da maior para a menor.

Exemplo:

    tokenizar("tudo bem hoje", ["tudo bem"])
      -> ["tudo bem", "hoje"]

Ela não produz:

* lema;
* análise morfológica;
* classe gramatical;
* sujeito;
* predicado;
* dependências;
* papéis semânticos;
* proposição;
* polaridade.

3.6. Busca atual

A busca pública passa por:

    ferramentas.busca.buscar_conhecimento()
      -> ConhecimentoDB.buscar_termo()

O índice principal é:

    conhecimento.termo_chave

O banco continua sendo consultado principalmente por correspondência textual
de termos ou expressões.

3.7. Roteamento atual

`core.roteador.rotear()` reconhece categorias como:

    SAUDACAO
    PERGUNTA
    ORDEM
    INFORMACAO
    DESCONHECIDO

E destinos como:

    INTERACAO
    CONHECIMENTO
    APRENDIZAGEM

A decisão usa padrões, pontuação, prefixos e expressões conhecidas.

O roteador não é um parser geral e não representa estruturalmente:

* afirmação;
* negação;
* hipótese;
* causa;
* consequência;
* sujeito e predicado;
* proposições encaixadas.

3.8. Contexto atual

`core.contexto_conversa.ContextoConversa` mantém estado em memória:

* últimos turnos;
* última frase normalizada;
* entidades ou menções ativas;
* tópico;
* desambiguação pendente;
* correção pendente;
* pergunta pendente;
* nome do interlocutor;
* contador de turno.

Esse contexto não é persistido no SQLite atual.

3.9. Composição atual

O compositor está em:

    core/composicao_resposta.py

Ele recebe dados já selecionados e monta uma resposta textual.

Ele não constrói:

* árvore sintática;
* grafo semântico;
* proposição;
* relação lógica;
* escopo de negação.

No modelo novo, ele deverá receber uma estrutura semântica pronta e não
reinterpretar a frase original.


4. RESULTADO DOS EXEMPLOS ATUAIS
--------------------------------

Os três exemplos foram executados em cópias temporárias dos bancos, sem alterar
os bancos originais.

4.1. "Hoje o vento está muito forte."

Resultado atual:

    normalização:
        hoje o vento está muito forte.

    tokens:
        hoje
        o
        vento
        está
        muito
        forte

    rota:
        desconhecido

    tokens encontrados no banco:
        nenhum

    grupos de sentido:
        nenhum

    resposta:
        desconhecimento

O sistema não identifica `vento` como entidade/sujeito, `forte` como
propriedade, `muito` como grau ou `hoje` como referência temporal.

4.2. "O cachorro está dormindo."

Resultado atual:

    normalização:
        o cachorro está dormindo.

    tokens:
        o
        cachorro
        está
        dormindo

    rota:
        desconhecido

    tokens encontrados no banco:
        nenhum

    grupos de sentido:
        nenhum

    resposta:
        desconhecimento

O sistema não constrói a relação:

    DORMIR(cachorro)

4.3. "O cachorro não está dormindo."

Resultado atual:

    normalização:
        o cachorro não está dormindo.

    tokens:
        o
        cachorro
        não
        está
        dormindo

    rota:
        desconhecido

    tokens encontrados no banco:
        nenhum

    grupos de sentido:
        nenhum

    resposta:
        desconhecimento

Não existe tratamento lógico específico para `não`.

O sistema não representa:

    NÃO(DORMIR(cachorro))

Nem diferencia estruturalmente a frase positiva da frase negativa.

4.4. Combinações novas

Quando duas expressões conhecidas aparecem juntas, o sistema pode reconhecer
cada unidade, mas não necessariamente compor a frase inteira.

Exemplo:

    "oi pessoal e boa noite"

Pode ser tokenizado como:

    ["oi pessoal", "e", "boa noite"]

Mas isso não produz uma estrutura composta nem duas proposições relacionadas.

Conclusão:

    reconhecer unidades existentes != compreender uma combinação nova


5. REPRESENTAÇÃO INTERMEDIÁRIA ALVO
------------------------------------

5.1. Estrutura geral

A frase deverá ser representada como um conjunto de camadas:

    Enunciado
      ├── texto original
      ├── texto normalizado
      ├── tokens e spans
      ├── formas lexicais
      ├── análises morfológicas
      ├── estruturas sintáticas candidatas
      ├── grafo semântico
      ├── proposições
      ├── contexto e referências
      ├── intenção
      └── incertezas/proveniência

Não haverá um único objeto plano que misture toda a informação.

5.2. Enunciado

Deve preservar:

* texto original;
* texto normalizado;
* idioma;
* variante;
* posição;
* pontuação;
* turnos;
* intenção provisória;
* análises alternativas;
* estado de processamento.

5.3. Token

Deve preservar:

* texto;
* posição inicial;
* posição final;
* pontuação;
* forma normalizada;
* possíveis expressões;
* origem da segmentação.

5.4. Forma lexical

É a ocorrência concreta, como:

    cães
    cachorro
    dormindo
    dormiu

Não é automaticamente o lema, o sentido ou o conceito.

5.5. Lema

É a forma de referência usada para agrupar flexões:

    cães       -> cão
    cachorros  -> cachorro
    dormindo   -> dormir
    dormiu     -> dormir

`termo_chave` do banco antigo não deve ser tratado como lema.

5.6. Lexema

É a unidade lexical abstrata que reúne:

* lema;
* comportamento gramatical;
* possibilidades de flexão;
* comportamento sintático;
* ligação com um ou mais sentidos.

Uma palavra polissêmica pode ser representada como:

    forma "banco"
      -> lexema candidato
      -> sentido financeiro
      -> sentido assento
      -> sentido margem de rio

O modelo deve permitir manter essas alternativas.

5.7. Sentido

É uma interpretação específica de um lexema em um contexto.

Um sentido pode possuir:

* definição;
* contexto de uso;
* classe gramatical;
* domínio;
* exemplos;
* relações;
* evidências;
* origem;
* estado de confirmação.

5.8. Conceito

É uma unidade semântica independente da forma linguística.

Exemplo:

    "cachorro"
    "cão"
    "cães"

podem se ligar a um conceito geral CANINO, sem que forma, lema, sentido e
conceito sejam a mesma coisa.

5.9. Entidade

Uma entidade é algo referido no discurso:

* pessoa;
* animal;
* objeto;
* lugar;
* fenômeno;
* entidade abstrata;
* entidade discursiva temporária.

`"o cachorro"` pode criar uma entidade discursiva sem criar automaticamente
uma entidade persistente.

5.10. Evento, estado e propriedade

Exemplos:

    DORMIR(cachorro)
    FORTE(vento)
    CANSADO(cachorro)
    ABRIR(João, porta)

O modelo deve permitir representar eventos, estados e propriedades sem
reduzir tudo a uma string.

5.11. Predicado e argumentos

Um predicado descreve uma propriedade, evento ou estado.

Argumentos recebem papéis:

* agente;
* sujeito;
* tema;
* paciente;
* instrumento;
* destino;
* origem;
* beneficiário;
* conteúdo;
* causa.

5.12. Proposição

Uma proposição é conteúdo estruturado que pode ser:

* afirmado;
* negado;
* perguntado;
* hipotético;
* provável;
* desejado;
* citado;
* condicionado.

Uma proposição não é automaticamente um fato confirmado.

5.13. Polaridade e escopo

Para:

    O cachorro não está dormindo.

O modelo deve produzir algo equivalente a:

    NÃO
      └── DORMIR(cachorro)

O escopo deve ser preservado para distinguir:

    Não acho que o cachorro esteja dormindo.

de:

    Acho que o cachorro não está dormindo.

5.14. Modalidade

Para:

    O cachorro provavelmente está dormindo.

O conteúdo é:

    DORMIR(cachorro)

Com modalidade:

    PROVAVELMENTE(conteúdo)

Isso não deve ser persistido automaticamente como fato confirmado.

5.15. Relações entre proposições

Para:

    O cachorro está dormindo porque está cansado.

Devem existir:

    P1 = DORMIR(cachorro)
    P2 = CANSADO(cachorro)
    CAUSA(P2, P1)

Para:

    O cachorro que estava dormindo acordou.

Devem existir:

    P1 = ACORDAR(cachorro)
    P2 = DORMIR(cachorro)
    P2 restringe a referência de "o cachorro"


6. CAMADAS DA NOVA ARQUITETURA
--------------------------------

6.1. Entrada e normalização

Entrada:

* texto bruto;
* metadados;
* horário;
* origem.

Saída:

* texto original;
* texto normalizado;
* spans;
* pontuação;
* segmentação preliminar.

Não deve:

* escolher sentido;
* declarar verdade;
* criar conhecimento;
* resolver toda a frase.

6.2. Análise lexical

Entrada:

* texto normalizado;
* pontuação;
* léxico;
* expressões candidatas.

Saída:

* tokens;
* formas;
* expressões candidatas;
* palavras desconhecidas;
* hipóteses de segmentação.

Não deve:

* escolher definitivamente o sentido;
* decidir função sintática;
* transformar toda sequência conhecida em expressão fixa.

6.3. Morfologia

Entrada:

* tokens;
* formas;
* regras morfológicas.

Saída:

* lemas;
* lexemas;
* classe gramatical;
* gênero;
* número;
* pessoa;
* tempo;
* modo;
* aspecto;
* voz;
* grau;
* formas nominais;
* alternativas.

Não deve:

* decidir sozinha o sentido;
* escolher o sujeito;
* criar fatos.

6.4. Sintaxe

Entrada:

* tokens;
* morfologia;
* pontuação;
* gramática.

Saída:

* constituintes;
* dependências;
* funções sintáticas;
* predicados;
* argumentos;
* estruturas candidatas.

Não deve:

* declarar fatos do mundo;
* gravar conhecimento;
* esconder ambiguidades.

6.5. Semântica

Entrada:

* sintaxe;
* morfologia;
* sentidos;
* contexto.

Saída:

* entidades;
* conceitos;
* eventos;
* estados;
* propriedades;
* papéis semânticos;
* relações;
* grafo semântico.

Não deve:

* transformar toda frase em fato;
* eliminar incertezas sem justificativa.

6.6. Proposições

Entrada:

* grafo semântico;
* sintaxe;
* polaridade;
* modalidade;
* contexto.

Saída:

* proposições;
* operadores;
* escopos;
* proposições encaixadas;
* relações entre proposições.

Não deve:

* confundir afirmação com confirmação factual;
* misturar conversa com mundo persistente.

6.7. Contexto

Entrada:

* turnos;
* entidades;
* proposições;
* referências;
* tempo;
* pendências.

Saída:

* saliência;
* coreferência;
* tópico;
* deíxis;
* esclarecimentos necessários.

Não deve:

* transformar contexto automaticamente em conhecimento persistente.

6.8. Conhecimento

Entrada:

* consultas estruturadas;
* formas;
* sentidos;
* conceitos;
* proposições;
* evidências.

Saída:

* candidatos;
* fatos;
* relações;
* fontes;
* evidências;
* estados.

Não deve:

* funcionar como parser;
* usar uma ficha como conceito automaticamente.

6.9. Inferência

Entrada:

* proposições;
* fatos confirmados;
* relações;
* regras;
* contexto.

Saída:

* conclusões;
* explicações;
* premissas;
* conflitos;
* proveniência.

Não deve:

* inventar premissas;
* transformar hipótese em fato;
* esconder contradições.

6.10. Intenção

Entrada:

* estrutura da frase;
* proposições;
* contexto.

Saída:

* ato de fala;
* objetivo;
* parâmetros;
* necessidade de esclarecimento.

Não deve:

* ser apenas uma lista de regex;
* executar diretamente uma ação.

6.11. Planejamento

Entrada:

* intenção;
* conhecimento;
* proposições;
* permissões.

Saída:

* plano de resposta;
* plano de ação;
* pedido de esclarecimento;
* evidências a apresentar.

6.12. Geração

Entrada:

* plano;
* resultado;
* evidências;
* incertezas.

Saída:

* resposta textual;
* esclarecimento;
* explicação.

O gerador não deve interpretar novamente a frase original.


7. ORGANIZAÇÃO DE BANCOS E TABELAS
-----------------------------------

7.1. Quantidade recomendada para a primeira versão

Quando a implementação for aprovada, a recomendação é:

    1 novo banco:
        aprendizado/bancos/linguagem.db

    14 tabelas iniciais:
        aproximadamente 125 colunas no total

O número é uma proposta de schema inicial para revisão. Não é autorização para
criar o banco antes da aprovação do desenho físico completo.

7.2. Tabelas iniciais propostas

    lexemas                  7 colunas
    formas_lexicais          8 colunas
    analises_morfologicas   11 colunas
    sentidos                 9 colunas
    conceitos                8 colunas
    sentidos_conceitos       6 colunas
    expressoes               8 colunas
    expressao_componentes    7 colunas
    proposicoes             12 colunas
    proposicao_argumentos    9 colunas
    fatos                    10 colunas
    relacoes_semanticas     11 colunas
    fontes                   8 colunas
    evidencias              11 colunas

    total                   125 colunas

7.3. Função de cada tabela

`lexemas`

Unidades lexicais abstratas, como DORMIR, CACHORRO e BANCO.

`formas_lexicais`

Formas concretas como dormindo, dormiu, cães e cachorra.

`analises_morfologicas`

Características da forma em uma análise: classe, gênero, número, pessoa,
tempo, modo, aspecto, voz, grau e confiança.

`sentidos`

Interpretações específicas de lexemas em contextos.

`conceitos`

Unidades semânticas independentes de uma única palavra.

`sentidos_conceitos`

Associação entre sentido e conceito, incluindo tipo da ligação, confiança e
estado.

`expressoes`

Expressões fixas ou semi-fixas, com grau de fixidez.

`expressao_componentes`

Componentes, ordem, literalidade, opcionalidade e restrições.

`proposicoes`

Conteúdo estruturado, polaridade, modalidade, tempo, escopo e estado.

`proposicao_argumentos`

Ligação de argumentos e papéis semânticos a uma proposição.

`fatos`

Proposições que receberam tratamento factual, com estado, validade e origem.

`relacoes_semanticas`

Relações tipadas entre conceitos, sentidos, entidades, proposições ou fatos.

`fontes`

Fontes de informação e sua confiabilidade.

`evidencias`

Trechos, explicações, estados e vínculos de proveniência.

7.4. Tabelas posteriores

Quando a inferência persistente e o fluxo novo de aprendizagem forem
estabilizados, podem ser adicionadas:

    regras_inferencia
    regra_premissas
    regra_conclusoes
    propostas_aprendizagem

Estimativa posterior:

    18 tabelas
    aproximadamente 160 colunas

Essas tabelas não precisam existir para o primeiro parser funcional.

7.5. O que não deve ser persistido inicialmente

Não colocar no SQLite permanente:

* tokens de cada frase comum;
* árvore sintática temporária;

8. RELACIONAMENTOS DO MODELO NOVO
---------------------------------

Diagrama conceitual:

    lexemas
      ├── formas_lexicais
      │     └── analises_morfologicas
      └── sentidos
              └── sentidos_conceitos
                        └── conceitos

    expressoes
      ├── expressao_componentes
      └── sentidos_conceitos/sentidos

    proposicoes
      ├── proposicao_argumentos
      ├── fatos
      └── relacoes_semanticas

    relacoes_semanticas
      └── conceitos, sentidos, proposicoes, fatos ou entidades

    fontes
      └── evidencias
             └── lexemas, sentidos, conceitos, proposicoes, fatos e relações

8.1. Por que lexemas e formas são diferentes

`dormir` e `dormindo` não são o mesmo registro linguístico.

    lexema:
        dormir

    forma:
        dormindo

A forma preserva o texto e os traços da ocorrência. O lexema agrupa formas
relacionadas.

8.2. Por que sentidos e conceitos são diferentes

Um lexema pode ter vários sentidos. Um conceito pode ser expresso por vários
lexemas.

    "cão"
    "cachorro"
    "canino"

podem participar de sentidos relacionados ao conceito CANINO, sem serem o
mesmo lexema ou a mesma forma.

8.3. Por que existe `sentidos_conceitos`

Porque a associação não precisa ser sempre um-para-um.

Um sentido pode se relacionar com vários conceitos, e um conceito pode ser
expresso por vários sentidos. A tabela de associação permite guardar:

* tipo de ligação;
* confiança;
* estado;
* evidência futura.

8.4. Palavra polissêmica

    forma "banco"
      -> lexema BANCO
      -> sentido BANCO_FINANCEIRO
      -> sentido BANCO_ASSENTO
      -> sentido BANCO_MARGEM

O parser pode manter hipóteses até que contexto e sintaxe desambiguem.

8.5. Flexão ligada ao lema

    forma "cães"
      -> forma_lexical
      -> lexema "cão"
      -> análise:
           classe substantivo
           número plural

    forma "dormiu"
      -> forma_lexical
      -> lexema "dormir"
      -> análise:
           pessoa terceira
           número singular
           tempo passado
           modo indicativo

8.6. Expressão

`bom dia` pode ser expressão fixa/conversacional.

`cachorro grande` tende a ser combinação produtiva:

    cachorro + modificador grande

`dar uma olhada` pode ser expressão semi-fixa, com componentes e variações.

`o cachorro está dormindo` é normalmente uma frase produtiva, não um item
lexical.

8.7. Proposição e argumentos

    proposição:
        predicado: DORMIR
        argumento:
            papel: sujeito/agente
            alvo: entidade cachorro

Os argumentos podem apontar para conceitos, entidades, eventos, proposições
ou outros elementos estruturados.

8.8. Fato e proposição

Uma proposição é conteúdo interpretado.

Um fato é uma proposição aceita com estado, fonte, validade e proveniência.

    "O cachorro provavelmente está dormindo."

gera uma proposição provável, mas não necessariamente um fato confirmado.

8.9. Relação semântica

Uma relação deve ter:

* tipo;
* origem;
* destino ou argumentos;
* direção;
* estado;
* contexto;
* fonte;
* confiança.

O campo legado `relacionados` não substitui essa estrutura.

8.10. Evidências e fontes

Uma fonte identifica de onde veio uma informação.

Uma evidência liga uma fonte e um trecho/justificativa ao registro que está
sendo sustentado.

A mesma proposição pode possuir várias evidências de origens diferentes.

A resolução de referência e a persistência factual são decisões diferentes.

pragmática.

`resposta_padrao`

É política ou saída conversacional. Não deve virar automaticamente sentido ou
fato.

`relacionados`

É associação legada sem direção e sem tipo confiável. Deve virar item de
revisão.

`exemplo_uso`

Deve ser preservado como exemplo/evidência. Não é automaticamente fato.

* compositor não consulta o banco por conta própria;
* compositor não reinterpreta texto.

12.13. Fase 12 — Critério de migração

13. TESTES DE CARACTERIZAÇÃO OBRIGATÓRIOS
-----------------------------------------

Os testes devem verificar estrutura, não somente texto de resposta.

13.1. Palavra conhecida em frase nova

Entrada:

    O cachorro está dormindo.

Esperado:

* cachorro reconhecido;
* dormir reconhecido;
* sujeito;
* predicado;
* polaridade positiva;
* frase inteira não precisa estar cadastrada.

13.2. Palavra desconhecida em estrutura conhecida

Entrada:

    O grifon está dormindo.

Esperado:

* sujeito parcialmente analisado;
* predicado reconhecido;
* entidade desconhecida localizada;
* restante da frase preservado.

13.3. Frase negativa

Entrada:

    O cachorro não está dormindo.

Esperado:

* mesmo predicado base;
* polaridade negativa;
* escopo de negação sobre dormir.

13.4. Modalidade

Entrada:

    O cachorro provavelmente está dormindo.

Esperado:

* polaridade positiva;
* modalidade epistêmica provável;
* não virar fato confirmado automaticamente.

13.5. Tempo e grau

Entrada:

    Hoje o vento está muito forte.

Esperado:

* vento;
* propriedade forte;
* modificador muito;
* referência temporal hoje.

13.6. Causa

Entrada:

    O cachorro está dormindo porque está cansado.

Esperado:

* duas proposições;
* mesma entidade;
* relação CAUSA.

13.7. Relativa

Entrada:

    O cachorro que estava dormindo acordou.

Esperado:

* proposição principal acordar;
* proposição encaixada dormir;
* ligação da relativa à entidade cachorro.

13.8. Agente, tema e instrumento

Entradas:

    João abriu a porta.
    João abriu a porta com a chave.

Esperado:

* agente João;
* tema porta;
* instrumento chave na segunda frase.

13.9. Negação de evento

Entrada:

    João não abriu a porta.

Esperado:

* negação com escopo sobre abrir;
* não confundir com ausência de busca.

13.10. Proposição encaixada

Entrada:

    João disse que Maria abriu a porta.

Esperado:

* evento dizer;
* fonte João;
* proposição encaixada;
* agente Maria;
* tema porta.

13.11. Flexão

Entradas:

    O cachorro dormiu.
    Os cachorros dormiram.
    A cachorra dormirá.
    Os cães estão dormindo.

Esperado:

* formas ligadas aos lemas;
* gênero/número/pessoa/tempo/modo/aspecto quando disponíveis.

13.12. Concordância

Entradas:

    Os cachorros estão dormindo.
    A cachorra está dormindo.
    Os cachorros está dormindo.

Esperado:

* duas primeiras compatíveis;
* terceira com conflito registrado;
* texto original preservado.

13.13. Expressão fixa

Entrada:

    Bom dia.

Esperado:

* expressão convencional;
* saudação;
* resposta social possível.

13.14. Combinação produtiva

Entradas:

    cachorro grande
    cachorro muito grande
    cachorro cansado

Esperado:

* estrutura sintática produtiva;
* não exigir cadastro de cada combinação.

13.15. Ambiguidade lexical

Entradas:

    Banco.
    Eu fui ao banco.
    Eu coloquei dinheiro no banco.
    O banco está quebrado.

Esperado:

* sentidos candidatos;
* seleção contextual quando possível;
* pergunta de esclarecimento quando necessário.

13.16. Ambiguidade sintática

Entrada:

    Vi o homem com o telescópio.

Esperado:

* análise instrumento;
* análise companhia/associação;
* alternativas preservadas.

13.17. Referência contextual

Sequência:

    O cachorro entrou na sala.
    Ele está dormindo.

Esperado:

* candidato de coreferência;
* ligação contextual;
* nenhum fato persistente automático.

13.18. Duas proposições e status

Testar:

* frase afirmada;
* frase provável;
* frase perguntada;
* frase negada;
* frase hipotética.

Esperado:

* conteúdo preservado;
* modalidade/polaridade diferentes;
* estado factual separado.

13.19. Não persistência indevida

No modo conversa:

* frase desconhecida não deve gravar conhecimento;
* uma menção não deve virar entidade global;
* uma afirmação não deve virar fato confirmado;
* hipótese não deve virar regra.

15. RISCOS DA NOVA ARQUITETURA
--------------------------------

15.1. Schema prematuro

Risco:

* cristalizar conceitos que ainda não foram discutidos.

Mitigação:

* revisar DDL completo antes de criar o banco;
* manter o schema como proposta até aprovação.

15.2. Confundir lexema, sentido e conceito

Risco:

* transferir a confusão do banco atual para várias tabelas.

Mitigação:

* testar polissemia;
* exigir exemplos;
* manter associações explícitas.

15.3. Excesso de colunas opcionais

Risco:

* tabelas difíceis de validar;
* dados sem significado claro.

Mitigação:

* separar entidades quando a cardinalidade exigir;
* usar constraints somente depois das regras definidas;
* não preencher desconhecido com valores falsos.

15.4. Parser grande demais

Risco:

* tentar cobrir todo o português antes de validar o núcleo.

Mitigação:

* começar com subconjunto pequeno;
* adicionar construções por testes;
* preservar fallback.

15.5. Falsa certeza na migração

Risco:

* transformar `tipo` em classe;
* transformar `termo_chave` em lema;
* transformar exemplo em fato;
* transformar `relacionados` em semântica.

Mitigação:

* staging;
* estados de candidato;
* revisão humana;
* origem legada preservada.

15.6. Perda de contexto

Risco:

* transformar referência de sessão em memória permanente.

Mitigação:

* separar objetos de contexto e persistência;
* exigir confirmação.

15.7. Perda de negação

Risco:

* continuar tratando "não" como token comum.

Mitigação:

* testes de escopo;
* representação explícita de operadores;
* comparação positiva/negativa.

15.8. Inferência sem explicação

Risco:

* conclusões sem premissas ou evidências.

Mitigação:

* registrar regra, premissas, conclusão e fonte.


16. ESTRATÉGIA DE ROLLBACK
--------------------------

Durante toda a migração:

* não apagar `conhecimento.db`;
* não apagar `relacoes.db`;
* não substituir o fluxo antigo de uma vez;
* usar bancos de desenvolvimento separados;
* executar o novo parser em modo sombra;
* manter fallback;
* registrar versões;
* criar checkpoints antes de mudanças.

Rollback por fase:

    Fase 0:
        restaurar branch/checkpoint e cópia dos bancos.

    Fase 1:
        descartar somente linguagem.db de desenvolvimento.

    Fase 2:
        retirar objetos novos sem alterar legado.

    Fases 3-7:
        desligar parser/API novos e usar adaptadores antigos.

    Fase 8:
        descartar staging/migração incompleta.

    Fase 9:
        desativar feature flag do novo fluxo.

    Fase 13:
        só arquivar legado depois de validação; nunca apagar sem backup.

19. DECISÃO FINAL DESTA ETAPA
-----------------------------

O projeto está dividido em duas realidades:

    sistema atual:
        reconhecimento textual de termos/expressões,
        busca de fichas,
        heurísticas,
        contexto curto,
        composição de respostas.

    sistema futuro:
        análise lexical,
        morfologia,
        sintaxe,
        semântica,
        proposições,
        polaridade,
        modalidade,
        contexto,
        conhecimento estruturado,
        inferência,
        intenção,
        planejamento,
        geração.

A direção física recomendada é:

    um novo linguagem.db
      -> 14 tabelas / aproximadamente 125 colunas inicialmente
      -> aproximadamente 18 tabelas / 160 colunas quando regras persistentes
         e propostas de aprendizagem forem incorporadas

Durante a transição:

* `conhecimento.db` será preservado;
* `relacoes.db` será preservado;
* `indice_codigo.db` continuará separado;
* `log_mudancas.db` continuará separado;
* `diagnostico.db` continuará separado;
* nenhuma migração será destrutiva;
* nenhum banco novo será criado antes da aprovação do schema físico.

A ordem correta é:

    documento consolidado
      -> schema físico completo
      -> aprovação
      -> criação de linguagem.db
      -> contratos Python
      -> léxico e morfologia
      -> parser
      -> semântica
      -> contexto
      -> conhecimento e inferência
      -> testes
      -> migração
      -> integração gradual
      -> desligamento controlado do legado
